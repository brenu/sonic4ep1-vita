## Startup evidence

Decompiled Java lives in `work/jadx/sources/`; apktool's authoritative smali is in `work/apkdecoded/smali/`. JADX emitted imperfect code in some unrelated methods, so verify semantics against smali when implementing callbacks.

1. `LoaderActivity.onCreate` calls `System.loadLibrary("s3e_android")`, triggering JNI_OnLoad, then invokes native `setART` and creates the initial view.
2. `LoaderThread` constructor calls `initNative()` after setting its loader, assets, file root and sensors. ARM disassembly shows that initNative caches Java method IDs extensively; it is not a standalone game init function.
3. `LoaderThread.getInstance` creates the thread, sets the view via `setView`, which invokes `setViewNative(LoaderView)`, then starts the thread.
4. `LoaderThread.run` waits for the view, then calls `runNative(fileRootAbsolutePath, packageResourcePath, nativeLibraryDir)`. The second argument is the APK path, not the OBB or a directory. This is a blocking native execution entry rather than a demonstrated per-frame renderer.
5. `LoaderView.glInit(int)` delegates to LoaderGL, and `glSwapBuffers()` handles swaps. LoaderGL supports choosing a context version at runtime; exact game GLES requirements still need confirmation. Native dynamic library lookup must be handled because core DT_NEEDED has no GLES library.
6. The expansion Java class is in JADX's `defpackage/s3eAPKExpansion.java`. It supplies `raw:/<externalStorage>/Android/obb/com.sega.sonic4epi/` and derives `main.6200011.com.sega.sonic4epi.obb` from package metadata. Translate these to the local file path when implementing the Vita bridge. Do not report a successful download/file check when the OBB is absent.
7. SoundPlayer uses native `generateAudio([SI)V`; LoaderThread also uses Android MediaPlayer channels and the APK contains music MP3 assets. Both PCM output and streamed music require implementation.

## JNI registration

The library exports JNI_OnLoad at ELF virtual address `0x3c43c`. Most Java entry points are registered through JNINativeMethod tables instead of exported `Java_*` symbols. The analyzer recovered 36 table candidates in the core library. [JNI_METHODS.md](JNI_METHODS.md) records them.

Key LoaderThread candidates are `initNative` at `0x3ad84`, `setViewNative` at `0x3a9f4`, and `runNative` at `0x3c204`. JNI_OnLoad disassembly shows the JNI RegisterNatives call. The new registry captures relocated runtime pointers instead of hard-coding these offsets. In pinned FalsoJNI, FindClass returns a duplicated name string and RegisterNatives is otherwise a no-op; the registry depends on that exact implementation and must be reviewed on upgrade.

Disassemblies of initNative, runNative and JNI_OnLoad are saved in `work/analysis/*.arm.txt`. Function names printed for stripped internal addresses are nearest-symbol labels and should not be mistaken for true function names.

### Memory and threading evidence

ELF 0x7022c calls mmap(NULL, rounded_size_plus_two_pages, 7, 0x21, -1, 0). It protects the first and last page as guard pages. ELF 0x7013c converts the engine's protection bits into POSIX READ=1/WRITE=2/EXEC=4 and calls mprotect. Thus the template's previous zero-filled malloc stub is insufficient: it lacks page isolation and executable/protection semantics.

The replacement tracks anonymous Vita memory blocks, rounds/validates lengths, converts protection bits to kubridge's different constants, flushes caches for executable transitions, and supports full-block unmapping. Unsupported file-backed/fixed mappings, partial unmapping, and untracked protection ranges return errors. Host tests cover policy arithmetic; hardware behavior is pending. The diagnostic adds a small allocation/protection/data-retention/unmap test without intentional faults.

ELF 0x82a18 initializes pthread attributes, uses either pthread_attr_setstacksize or pthread_attr_setstack for the supplied stack, then calls pthread_create. The new setstack wrapper uses the existing Bionic-to-native attribute indirection. Removed the unconditional 512 KiB override for explicitly provided attributes, which could invalidate a supplied stack's bounds. Allocation failures in attribute initialization are handled.

## Boot probe 04 — software Canvas bridge

Probe 03 gets past the previous glReInit stop and reaches the software doDraw callback. Graphics initialization for its error dialog returns and the dialog is visible. The new log is preserved in work/hardware/boot-03.log.

LoaderView.doDraw's Java body checks m_FullScreenBitmap and m_UseGL, then copies m_Pixels into an RGB_565 bitmap and posts a Canvas. LoaderView.surfaceChanged supplies width/height/a persistent int[]/m_NewlyCreated via native setPixelsNative. Merely skipping doDraw would omit this startup presentation, and not supplying the native pixel-array contract would leave the runtime's software surface incomplete.

Ghidra export work/decompiled/setPixelsNative.c confirms native registration of the array through NewGlobalRef and recording of width/height. Newly-created surfaces also update orientation/reinit and signal the surface-change event. That event is exported as surface_event.c (ELF 0x7e4d4). The bridge now allocates/zeros the JNI int[] after initNative/setViewNative and calls setPixelsNative with the original signature and newly-created flag. The shared array is retained for the process because the runtime can replace its own global references without owning the bridge's reference.

The new software path converts 0xAARRGGBB integer values to RGB565, matching the selected bitmap's non-alpha format. It uploads the 960x544 buffer to a texture and draws a full-screen quad; matrix/client-pointer/render state touched by the blit is explicitly restored. It avoids the pinned driver's attribute-stack implementation. When GLES is active, doDraw returns without an extra draw/swap, matching the Java guard. GLES context version 0 is accepted as Android's default-version request.

This is a startup Canvas implementation, not evidence of correct rendering or complete graphics lifecycle handling. The host color/order/bounds and draw-guard tests pass; GPU presentation, native surface-event timing and later game state need the next Vita run. Logs record surface registration, the first software frame and any GL error. Input/audio/extension Java methods remain unfinished.

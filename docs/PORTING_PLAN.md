## Execution plan and acceptance gates

1. Inventory tools and inputs; record hashes, APK metadata, ABI, ELF imports/exports/attributes, OBB format and contents. Extract only into local generated directories. Produce repeatable analysis tooling and saved reports.
2. Check feasibility: native ARMv6/v7 game code, graphics API, engine/runtime, audio dependencies, and how much game logic is in Java. Stop the SO-loader route if binary architecture or runtime makes it unsuitable, documenting evidence and alternatives.
3. Decode DEX with apktool (available) and preferably JADX. Trace Java activity lifecycle, native declarations, JNI registration, surface initialization, rendering, controls, file paths, expansion file access, audio and callbacks. Record exact signatures and call order. Use ARM disassembly/Ghidra where exports are insufficient; do not guess function addresses or ABI.
4. Obtain and pin the guide's loader base and its submodules. Preserve upstream licensing. Adapt game name, title ID, data paths, native module loading, imported symbols, and lifecycle only after evidence establishes the necessary interfaces.
5. Implement compatibility layer incrementally: Bionic/libc and pthread ABI, Java callbacks, APK/OBB access, GLES-to-vitaGL rendering, audio, controller/touch mapping, save paths, suspend/resume. Avoid silent fake success for unsupported essential functions; log and fail clearly.
6. Compile a known SDK sample first, then the game loader with VitaSDK softfp and compatible libraries. Resolve compiler/linker errors. Package only loader and original redistributable project assets; game binaries/data stay in a private staging directory outside the VPK.
7. Test on an actual Vita with kubridge and required graphics runtime. Capture unresolved imports, startup logs/crashes, rendering, audio, controls, saves, memory use and sustained gameplay. Each crash fix needs evidence from the exact APK hash. Do not claim success without hardware validation.
8. Maintain this file plus a README with exact build/staging commands, tool requirements, work completed, outstanding uncertainties and the next resumption command.
